# 技术指南

[English](TECHNICAL_GUIDE.md) | 简体中文

## 1. 规划模型

本技能把项目视为受控回路，而不是静态清单。

### 1.1 规划对象

每条重要陈述都应标明类型：

| 对象 | 回答的问题 |
|---|---|
| Goal | 用户可见的结果是什么？ |
| Metric | 结果如何度量？ |
| Constraint | 什么不可违反？ |
| Fact | 已观察到什么、来源在哪？ |
| Assumption | 暂时采信但未验证的是什么？ |
| Decision | 选了哪个方案、为什么？ |
| Risk | 什么会让目标失败？ |
| Dependency | 什么外部状态或前置条件阻塞进展？ |
| Evidence | 哪个观察支持或推翻结论？ |

最小目标链：

```text
goal -> metric -> baseline -> target -> measurement -> deadline/stop -> non-goal
```

### 1.2 计划分辨率

- L0 回答系统/项目"是什么"。
- L1 把 L0 转成里程碑：目标、DoD、Gate、依赖、触发器与状态。
- L2 只把当前一两个里程碑展开成最小可执行动作。

计划应在当前焦点附近足够细，在远处刻意保持粗略。

## 2. 迭代循环

每个有意义的回合包含五拍：

1. 陈列完整计划快照与 `Δ vs 上轮`。
2. 执行当前最小动作。
3. 观察硬证据，而非推断成功。
4. 修订受影响的计划项与假设。
5. 自问目标、证据、阻塞项与证伪策略是否仍成立。

每轮以恰好一个结果收束：

- `CONTINUE`：路径仍有支撑，下一步有可检验产出。
- `PAUSE`：缺少资源或外部事实，无法安全推进。
- `SCOPE-DOWN`：缩小范围保住价值，并重写 DoD 与 Non-Goals。
- `PIVOT`：核心假设或选型被证伪。
- `STOP`：目标已达成、风险不可接受，或继续投入不值得其成本。

## 3. 变更安全

每个改状态的动作都走变更协议：

```text
READ -> CLASSIFY -> PROTECT -> CHANGE -> VERIFY -> RECONCILE -> ROLLBACK/RECORD
```

协议按资产区分对待：源码编辑、用户数据库迁移、秘密文件更新和进程重启不是等价变更，不得共用同一套默认流程。

变更运行态或部署目标前，先比对计划与现实：文件版本或 hash、服务状态、生效配置、健康端点、端口状态、数据库迁移版本与已部署版本。

## 4. 完成判定

完成分层：

1. `artifact-complete`：目标产物存在。
2. `functional-verified`：行为通过适用的功能检查。
3. `operational-verified`：真实进程、部署或集成链路可用。
4. `outcome-validated`：用户目标或关键指标被观察到。

计划稳定并不足够。连续两轮无 diff 是有用的收敛证据，但不能替代项目声明的完成层级。

## 5. 评审与停滞

当 Gate 不可逆、影响多个下游里程碑、或上一轮裁决有争议时，进行对抗式评审。评审人检查同一工件快照，必须引用具体证据或反例；重复措辞不算独立发现。

停滞断路器在以下情况触发：连续两轮没有新的 E2 以上证据、关键路径未缩短、假设被复用却没有验证设计、缩范围后未重新定基线。下一个动作必须是证伪实验、暂停、转向或停止。

## 6. 状态与恢复

Git 仓库用 commit/tag 记录源码与配置的版本谱系；非 Git 环境用 manifest 描述路径、版本、备份位置、服务状态与验证命令。`state.json` 存紧凑的机器可读摘要，人类可读账本放在项目状态文件里。

恢复时先把保存的状态与真实环境对账。冲突时以现实为准，受影响条目降为 `[待重估]`。

## 7. 未来工具化

本技能刻意保持文本优先。至少跑过三个真实项目之后，记录反复出现的违例与险情。工具候选按严重度和频率双维度筛选：罕见的灾难性不变量不因罕见而忽略，常见低风险检查则是效率工具的好候选。

## 8. 发布就绪

发布技能或技术文档时，不要直接发布混杂的工作目录。先用显式白名单构建干净的暂存目录，再执行：

```text
白名单 -> 内容扫描 -> 引用检查 -> 范围检查
       -> 发布检查 -> 发布 -> 远程复核
```

内容扫描覆盖本地路径、个人数据、凭据、Cookie、Token、内部主机、部署细节、私有仓库链接与真实测试数据。引用检查覆盖版本号、章节号、仓库相对路径、模板引用、占位符与 README 入口。范围检查删除项目专属运维细节，只保留可异地复用的机制。

发布后独立检查远程可见性、默认分支、提交、文件清单与 README 可访问性。本地提交不是远程发布成功的证据。仓库创建或推送失败时，停止依赖性验证步骤并报告真实远程状态。

发布检查必须记录限制。扫描干净只证明已定义的检查通过，不证明不存在未知的敏感信息。

## 9. 运行期纪律

凡产出长驻服务、定时任务、批量管道或第三方依赖的项目，追加五条规则：

1. **外部依赖健康**：为关键上游登记探针。占位数据（如全 `127.0.0.1` 节点）、域名失效与上游 EOL 意味着依赖已死——走替代路径，不当瞬时错误重试。
2. **静默失败类别**：HTTP 200 但空体或提前 EOF、占位内容与静默截断是独立于显式报错的失败类；验证查内容有效性而非仅状态码，同类静默失败计入回炉计数。
3. **自动化三件套**：长驻循环带硬超时、连续失败熔断与并发上限。恢复按有界重试、隔离连接/实例、受控重启、受控重建分级进行；重建须有幂等性、恢复点、速率限制、最大次数与人工升级条件。跨天存活的系统再加定时健康检查，监控自身也要有存活确认。
4. **批处理幂等**：批量任务可重跑，支持 dry-run 预览与增量对账；重复执行绝不产生重复数据。
5. **降级阶梯**：降级链预先设计并写明各级触发条件；故障期间临时拼凑降级路径视同方向性缺陷，须回炉重规划。

## 10. 状态与评审工件

随包模板是记录工件，不是装饰性清单：

- `state.json` 是规范的可续跑状态投影。项目只读时应在其他位置记录 `state_persistence: unavailable`，不得为了创建状态文件而改项目。
- `intake.md` 建立目标链与类型化规划账本。
- `plan.md` 保存 L0/L1/L2 血缘、里程碑 Gate、完成层级与证据锚点。
- `round.md` 记录 Diff 计数、失败分类、回炉层级、停滞检查与结果详情。
- `change-record.md` 证明变更协议的每一步，并把需求变化与实现变化分开记录。
- `gate-review.md` 与 `gate-verdict.md` 记录独立评审、锚点发现以及采纳/驳回裁决。
- `release-check.md` 记录七阶段发布状态机；前置阶段或远程验证未解决时停止发布。

按任务使用最小适用工件集，但不能因为记录不方便就省略必要记录。没有证据锚点的模板条目仍是开放事项，不是完成证明。
